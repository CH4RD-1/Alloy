# Alloy — web app scaffold

A Next.js (App Router, TypeScript, Tailwind) starting point for Alloy, backed by Supabase (Postgres + Auth + Storage). This is a first-pass scaffold, not a finished app — see `../schema.sql` for the database schema and the `alloy-saas-roadmap` project doc for the overall plan.

## Setup

1. Create a Supabase project.
2. Run `../schema.sql` against it (SQL editor, or `psql`), then work through the "Row Level Security" section at the bottom of that file — enable RLS and add a tenant-isolation policy on every org-scoped table before storing real data (only `projects` and `tasks` are done as worked examples there).
3. Copy `.env.example` to `.env.local` and fill in your Supabase project URL + keys (Project Settings → API).
4. `npm install`
5. `npm run dev` — http://localhost:3000

## Testing locally

There's no signup/org-creation UI yet, so getting from a fresh Supabase project to a populated List view takes a few manual steps:

1. In your Supabase project dashboard, go to **Authentication → URL Configuration** and add `http://localhost:3000/**` to the allowed redirect URLs — without this the magic-link email will silently fail to sign you in.
2. `npm run dev`, go to `/login`, enter your email, and request the magic link. This creates your `auth.users` row (and, via the trigger at the bottom of the `users` table section in `schema.sql`, a matching `public.users` row) immediately — you don't need to click the email yet.
3. In the Supabase SQL editor: `select id, email from auth.users order by created_at desc limit 5;` to get your new user id.
4. Open `../seed.sql`, paste your id in for `v_user_id`, and run the whole block. It creates one org, its 5 workflow statuses and the 7 standard transitions between them (see "Manage workflow & roles" below — without these, tasks couldn't change status at all), a project, a team, a parent task with two subtasks and a milestone, and a tag — enough to see the List view's expand/collapse, status colors, and tag chip actually do something.
5. Go back to the email and click the magic link — it should land you on `/dashboard` (via `app/auth/callback/route.ts`, which exchanges the link's code for a real session) showing the seeded tasks.

## What's here

- `app/login` — magic-link sign-in stub (Supabase `signInWithOtp`).
- `app/auth/callback` — completes the magic-link sign-in (exchanges the emailed code for a session). Required for `/login` to actually work, not optional plumbing.
- `app/dashboard` — the **Dashboard**, **List**, **Buckets**, **Gantt**, **Calendar**, **Knowledge base**, and **Assets** views, ported from the prototype (see below), switchable via the tabs above the task table.
- `app/portal/[orgSlug]` — the public customer Portal. This is what a QR code should point at, e.g. `/portal/acme?asset=<asset-id>` for an asset-scoped ticket.
- `app/api/tasks` — example authenticated CRUD route.
- `app/api/webhooks/email` (Postmark) and `app/api/webhooks/whatsapp` (Twilio) — the working multi-channel ticket-intake adapters discussed in the roadmap — see "Channel adapters" below.
- `lib/supabase/client.ts` / `lib/supabase/server.ts` — browser + server Supabase clients (`@supabase/ssr` pattern).
- `lib/types.ts` — TypeScript types mirroring `schema.sql`; extend as the schema grows.
- `middleware.ts` — refreshes the Supabase auth session on every request.

## List view, task panel, search, and create (ported)

Ported from the prototype's `renderListView()` / `listRowHtml()` plus its task detail panel, across these pieces:

- `lib/list-view.ts` — pure row-shaping logic (no React, no Supabase): builds parent/child rows with derived fields (dependency count, the "blocked" flag, subtask completion) the same way the prototype computed them client-side over its in-memory task array. `flattenRows()` turns that parent/child tree into a flat lookup-by-id list, used by the panel and the link picker. Per-template vocabulary (Task/Ticket, Team/Queue) lives here too.
- `lib/tasks-data.ts` — `getWorkspaceData()`: resolves the signed-in user's org, then loads everything the list + panel need for it (tasks, statuses, workflow transitions, teams, projects, links, tags, doc-counts, assets, and org members for the assignee dropdown).
- `lib/actions.ts` — Next.js server actions for every mutation (status moves, field edits, tags, subtasks, links, create, delete). These run with the signed-in user's own Supabase session, not a service-role client, so tenant isolation comes from RLS once it's filled in everywhere — but workflow permission (`allowed_roles`, the subtasks-complete gate) is checked by hand here, since RLS can't express that.
- `components/task-list-view.tsx` — the list rendering; rows are now clickable (opens the panel) with expand/collapse for subtasks still kept as local state.
- `components/task-panel.tsx` — the slide-over task detail panel: editable title, status with role-gated "move to" buttons wired to real `workflow_transitions`, assignee/team/dates, tags (add/remove), subtasks (view + quick-add), dependency links (view, add, remove — including the helpdesk Concurrent/Clone→Block downgrade rule from `schema.sql`), and delete.
- `components/new-task-panel.tsx` — the "+ New task" form, reusing the same panel shell.
- `components/tasks-workspace.tsx` — the client-side wrapper tying it together: search (client-side, filtering top-level rows by title/description/assignee/tags — matches the prototype's `matchesFilters`, which also only filtered top-level tasks), and the open/close state for both panels.

The status colors, chip styles, and grid/panel layout in `app/globals.css` are copied from the prototype's CSS tokens so this looks like a continuation of the same product rather than a restart.

**Known simplifications in this pass:** the `require_checklists_complete` workflow gate isn't enforced (checklist task-objects haven't been ported, so there's nothing to check); the link picker doesn't exclude tasks that already have a link to the current one, so adding a duplicate link surfaces as an error rather than being hidden from the list; and there's no confirmation step beyond a browser `confirm()` on delete.

## Buckets view (ported)

Ported from the prototype's `renderBucketsView()` — a kanban board with one column per team, drag-and-drop to reassign a task's team:

- `lib/buckets-view.ts` — pure grouping logic: buckets tasks by team name (merging same-named teams across projects, like the prototype's `teamGroupsFor()`, though with only one project seeded so far that merge behavior is mostly latent), always including empty teams as columns, plus a trailing "No team" column for unassigned tasks.
- `components/buckets-view.tsx` — the board itself. Drag a tile to another column to change its team (`updateTaskFields(taskId, { team_id })`, the same server action the task panel's team dropdown already uses). Unlike List, Buckets shows every task including subtasks, and search filters each one individually rather than only top-level rows — matching the prototype's `matchesFilters` applied to the flat `TASKS` array.

**Known simplification:** the prototype panned the board horizontally via custom click-drag-on-blank-space handlers (`bucketsPan`); this port uses the browser's native horizontal scrollbar instead (`overflow-x: auto`) since it covers the same need without the extra JS.

## Gantt view (ported, read-only)

Ported from the prototype's `renderGanttView()`, deliberately scoped down to a **read-only** first pass — the prototype's drag-to-move/resize bars, drag-from-a-node-to-create-a-link, and the "External nodes" on/off toggle are all left out (see below). Clicking a bar or label opens the task panel to edit dates/status instead.

- `lib/gantt-schedule.ts` — pure date math, ported from the prototype's `propagateSchedule()`/`autoArrange()`: given tasks with their Block/Concurrent/Clone links, computes the schedule the whole graph settles into (compact against blockers to a fixed point, then reconcile Concurrent's locked shared due date and Clone's mirrored schedule). No React, no Supabase — just `ScheduleTask` in, changed `{id, start, due}` out.
- `lib/gantt-view.ts` — pure layout logic: turns the existing List-view `TaskRow` tree into visible Gantt rows (expand/collapse, Helpdesk-project tasks excluded since they're unscheduled — same as the prototype), then the date-range/day-width/row geometry, month and Monday gridlines, and dependency-connector line endpoints.
- `components/gantt-view.tsx` — renders that layout as an SVG (bars, milestone diamonds, connector lines, today-line, legend, expandable label column) and the **Auto-arrange** button.
- `lib/actions.ts` → `autoArrangeSchedule(orgId)` — the one-shot server action behind that button: fetches every non-Helpdesk task + link in the org, runs `autoArrangeCompute()`, and writes back only the tasks whose start/due actually changed. This is where the prototype's scheduling cascade — client-side and trusting the browser there — becomes server-authoritative, per the roadmap doc's "server-authoritative business logic" principle.

**Known simplifications in this pass, to keep it to a read-only chart:**
- No drag-to-move/resize bars, no drag-from-a-node-to-create-a-link, and no floating link-edit menu — Auto-arrange (a bulk, one-shot reschedule) stands in for continuous drag-driven rescheduling.
- No "External nodes" toggle. The prototype had two connector-routing modes; this port always uses the later "External nodes: Off" geometry — connectors run straight from bar edge to bar edge, since there's no interactive node to route around when nothing's draggable.
- Bars are always filled with their team's color at full saturation (no "muted for other people's tasks" treatment), and bar labels always sit just outside the bar rather than being fit inside wide ones in a contrast-computed text color — both were dropped to avoid needing client-side color math (`mixHex`/contrast) reading CSS custom properties at render time, which risks a light/dark flash on first paint in a server-rendered app the prototype (browser-only, `localStorage`-backed) never had to worry about.
- Concurrent/Clone connectors are drawn as one line per linked pair rather than the prototype's two (lead + trailing) lines for Clone.

- `components/task-panel.tsx` — gained a "Linked docs" section mirroring the existing "Links" section, using the same `linkDocToTask`/`unlinkDocFromTask` actions, so the List view's docs-count icon (previously always 0) now means something.
- `lib/actions.ts` → `createDoc`, `updateDocFields`, `deleteDoc`, `linkDocToTask`, `unlinkDocFromTask`.
- `app/portal/[orgSlug]/page.tsx` — the public Portal's knowledge-base column now renders the same doc-card look (title + stripped preview) for published articles, instead of a bare `<li>` list.

**Known simplifications:** the prototype's Knowledge base used a full contenteditable rich-text editor (Title/Subtitle/Normal block styles, inline images inserted as data-URIs) with a separate stacked side panel so an article could stay open beside its linked task. The prototype's "reference doc" vs. "article" distinction was also dropped; by the prototype's own latest version everything had converged on the article type anyway (see `normalizeLoaded`'s doc migration), so this port only has one kind of doc.

## Task-panel objects (ported: notes, files, sketches + checklists)

Ported from the prototype's `objectsSectionHtml()`/`obj-menu`/`obj-card` system — an "Attachments" section on the task panel, sitting right after Tags (same position as the prototype's panel layout).

- `lib/types.ts` — `TaskObjectKind` (`note | file | sketch | checklist | form`), `TaskObject`, `TaskObjectFile` (the Storage-backed side of a `file`/`sketch` object — a 1:1 row pointing at the actual bytes), `ChecklistItem`.
- `components/task-objects.tsx` — the "Attachments" section: a `+` button opens a menu to add a text note, upload a file, open a sketch pad, or add a checklist; each renders as its own card with a remove button. A note is a plain textarea (saved on blur into `task_objects.content.text`); a checklist has add/toggle/relabel/remove on its items plus a done-count line; a `FileCard` shows a clickable image thumbnail (opens a lightbox) or a generic-icon download link for anything else, plus the filename and size; a `SketchCard` is a 420×200 `<canvas>` with pointer-event drawing (a straight port of the prototype's `initSketchCanvases()` — refs, not state, for the mid-stroke drawing position, so a pointermove never triggers a re-render) that saves a PNG on every stroke end, plus a "Clear sketch" button that reuses the exact same save path with a blanked canvas.
- `lib/storage.ts` (NEW) — the bucket name (`task-attachments`), the 4MB size cap (matching the prototype's own `MAX_BYTES` on its data-URI uploads — never a real infra limit, just a "don't choke the browser" guard that's just as reasonable a cap now that files go to real Storage), the `org_id/task_id/task_object_id/<filename>` key layout, and a filename sanitizer. Kept as a plain module rather than folded into `lib/actions.ts` because a `"use server"` file can only export async functions.
- `lib/actions.ts` → `createFileTaskObject` (creates the `task_objects` row and uploads in one step, rolling the row back if the upload fails — a `file` object with no bytes is meaningless), `saveSketchImage` (uploads/overwrites a fixed `sketch.png` key with `{upsert: true}` and upserts the `task_object_files` row on conflict), `createTaskObject` (widened to also accept `"sketch"` — its canvas starts empty, same as a checklist starts with no items, so it needs no upload at creation), `updateNoteText`, `deleteTaskObject` (now also best-effort removes the associated Storage object first, since a cascaded-away DB row doesn't delete anything from the bucket), `addChecklistItem`, `updateChecklistItem`, `removeChecklistItem`.
- `lib/tasks-data.ts` — `getWorkspaceData()` now also fetches every `file`/`sketch` object's `task_object_files` row and batch-generates signed URLs for them (`taskObjectFileByObjectId: Map<objectId, TaskObjectFile & {url}>`), threaded down to `TaskObjects` alongside `checklistItemsByObject`.
- `next.config.mjs` — raised `experimental.serverActions.bodySizeLimit` to `5mb` (Next's own default is 1MB, smaller than the 4MB attachment cap this ports).
- `schema.sql` / `task_attachments_storage.sql` (NEW incremental patch) — a `unique` constraint on `task_object_files.task_object_id` (needed for the sketch pad's upsert-on-conflict re-saves — this table existed since the earlier pass but nothing wrote to it yet, so the constraint was never added), the `task-attachments` Storage bucket (created **private**, not public), and RLS on `storage.objects` scoped to that bucket. Run the patch once against your existing database the same way as the earlier RLS patches.

**Why a private bucket + signed URLs instead of a public one:** a public Supabase Storage bucket's URLs need no auth at all — anyone with the link can fetch the object forever. In a multi-tenant app that means a leaked link would expose another org's file permanently. This keeps the bucket private and has `getWorkspaceData()` generate short-lived (1 hour) signed URLs server-side on every page load instead — the tradeoff is a URL that goes stale if you sit on a page for over an hour without it refreshing, which a normal `router.refresh()` (triggered by any action) resets.

**Real difference from the prototype, disclosed:** the prototype's files were never actually downloadable — `dataUrl` was an in-browser base64 string with nowhere to go. A non-image file's card here is a genuine download link (`<a href={signedUrl} download>`) pointing at the real object in Storage.

**Known simplification:** `form` still isn't rendered in the task panel (an object of that kind still shows the inert "not supported in this view yet" stub) — it's created only by the Portal's `submitPortalRequest` service-role flow, and rendering a submitted form's answers back in the internal panel is a separate, not-yet-built piece.

## Portal request form (ported: form templates + intake)

Ported from the prototype's `renderFormsManagerPanel()` (template builder) and `renderPortalView()` (the public request form) — together these turn the Portal from a read-only knowledge base into a real ticket-intake channel.

- `lib/types.ts` — `FormFieldType`, `FormField`, `FormTemplate`, matching the `form_templates`/`task_object_forms` tables that were already in schema.sql from the earlier pass (only `task_objects.kind = 'form'` itself wasn't wired up).
- `components/form-templates-panel.tsx` — an internal "Manage form templates" panel (a `small-btn` next to `+ New {task}`): create a template, rename it, toggle "Visible on Portal", add/remove fields (text/paragraph/number/select/yes-no/date, with comma-separated options for select), delete a template (blocked while any submission references it).
- `components/portal-request-form.tsx` — the public form: pick a template → name/email/summary → the template's own fields, rendered with the same control-per-type logic as the prototype's `formFieldControlHtml()` → submit. Shows an empty state when the org has no portal-visible templates yet, and a "Submit another request" reset after success.
- `app/portal/[orgSlug]/page.tsx` — now a two-column layout: the request form on the left, the knowledge-base list on the right (was KB-only before). Accepts `?asset=<id>` and pre-fills the summary field with it — see simplification below.
- `lib/actions.ts` → `createFormTemplate`, `updateFormTemplate`, `deleteFormTemplate`, `addFormField`, `removeFormField`, and `submitPortalRequest`.

**The interesting part is `submitPortalRequest`.** Every other write in this app goes through the normal RLS-bound Supabase client, gated by `requireUser()` — but a Portal visitor isn't logged in and can never satisfy `is_org_member()`, so that path is structurally unavailable here. This action instead uses `createServiceRoleClient()` (already sitting in `lib/supabase/server.ts` from the Phase-0 scaffolding, unused until now) to bypass RLS entirely for this one write, after first re-validating server-side that the template belongs to the org and is actually `portal_visible` — the client can't be trusted to enforce that. It then: finds-or-creates a `contacts` row by lowercased email (or always creates one if no email was given), picks the org's first `is_helpdesk` project if one exists (falling back to the first project otherwise, matching how the Buckets/Gantt views already treat helpdesk tasks as unscheduled — null start/due dates when landing in a helpdesk project), inserts the task with a templated description, and records the submission as a `task_objects` row of kind `form` plus its answers in `task_object_forms`.

Also added: a `form_templates_public_read` RLS policy (`portal_visible = true`, select-only — writes stay members-only via the existing tenant-isolation policy), following the same OR'd-permissive-select pattern as `docs_public_read`. This needs a one-time migration against your existing local database — see `portal_form_templates_rls.sql`.

**Known simplifications:** the prototype's Portal also had a live-chat widget, but it was always a labeled placeholder with no backend behind it in the prototype either, so it wasn't ported. The `?asset=` pre-fill only carries the asset id into the summary text as `Regarding asset <id>` — it can't look up or display the asset's actual name yet, because `assets` has no public-read RLS policy and Assets management itself isn't built beyond display.

## Channel adapters: email + WhatsApp (built)

Replaces the two TODO-only webhook stubs this port shipped with from the start (`app/api/webhooks/email/route.ts`, `app/api/webhooks/whatsapp/route.ts`) with real, working adapters — the multi-channel ticket intake the roadmap doc's own design principle called for: "each channel is just an adapter... normalize into one internal ticket-intake path." Picked concrete providers rather than staying generic, matching the roadmap's own recommendations: **Postmark** for email (its inbound-parse webhook + send API), **Twilio** for WhatsApp (no business-verification wait, unlike going straight to Meta's Cloud API). No new schema — `contacts`, `tasks.channel`/`.contact_id`/`.external_thread_ref`, and `ticket_messages` were all already fully built in an earlier pass, just never written to or read from by any app code until now.

- `lib/channel-verify.ts` (NEW) — the provider-specific bits with no business touching the database: `parseMailboxHash()` (email's routing scheme — see below), `replyToAddressForTask()`/`replyToAddressForOrg()`, and `verifyTwilioSignature()` (Twilio's HMAC-SHA1 webhook signature check, via Node's built-in `crypto` — no SDK dependency needed for either provider; both adapters talk to their REST APIs with plain `fetch()`).
- `lib/actions.ts` → `intakeTicket()` (the channel-agnostic "one internal ticket-intake path": find-or-create a `Contact`, find-or-create the task, insert an inbound `ticket_messages` row, treat a re-delivered webhook's duplicate `external_message_ref` as a safe no-op via the existing unique index rather than an error) and `sendChannelReply()` (the outbound half — insert an outbound `ticket_messages` row and actually call the provider's send API). Also factored `findOrCreateContact()`/`findIntakeProject()` out of `submitPortalRequest` (unchanged behavior) since `intakeTicket` needed the exact same lookups — one copy instead of two.
- `app/api/webhooks/email/route.ts` (Postmark) / `app/api/webhooks/whatsapp/route.ts` (Twilio) — parse each provider's native payload, verify the request is genuinely theirs, resolve which org/task it belongs to, and call `intakeTicket()`.
- `components/task-panel.tsx` → `ConversationSection`, a new panel section (only shown on `email`/`whatsapp` tasks) — the message thread as chat-style bubbles plus a reply box wired to `sendChannelReply()`.
- `.env.example` — the new provider credentials, documented inline.

**How each channel figures out "which task is this."** Email has no equivalent of a phone number to key off, so every ticket address this app hands out is `<anything>+<hash>@EMAIL_INBOUND_DOMAIN`: a brand-new ticket goes to `support+org-<slug>@...` (a public address you'd publish), and a reply goes to `support+task-<task-id>@...` — this app puts that exact address in the `Reply-To` header of every outbound message it sends, so hitting "reply" in any mail client naturally threads back to the right task with zero References/In-Reply-To header parsing required. Postmark splits the `+tag` into its own `MailboxHash` field for you; `parseMailboxHash()` is the one place that string gets interpreted. WhatsApp has no such trick — a phone number is all a webhook has to go on — so a new inbound message reuses the contact's most recent still-open `whatsapp` task if they have one, or starts a new one otherwise.

**Two disclosed, real limitations, not simplifications-for-parity like most of this README's other notes** (the prototype never had channel adapters to compare against — there's no "prototype behavior" to match here): (1) the WhatsApp adapter is single-tenant per deployment — one Twilio sender number (`TWILIO_WHATSAPP_FROM`) serves exactly one org (`WHATSAPP_ORG_SLUG`), since a real per-org WhatsApp sender needs its own Meta business verification this app can't provision on a customer's behalf; multiple orgs on WhatsApp means multiple deployments for now. (2) `sendChannelReply` checks WhatsApp's 24-hour customer-service window (outside it, Meta/Twilio require a pre-approved message template rather than free-form text) and refuses rather than silently failing at Twilio's end, but this app doesn't manage templates at all — restarting a stale conversation isn't possible yet, only continuing a recent one.

- `components/asset-icon.tsx` — the icon set as React components (laptop/desktop/monitor/phone/keyboard/mouse/toolbox/hard hat/boots/trousers/other), SVG paths copied verbatim from the prototype's `ASSET_ICONS`.

- `lib/actions.ts` → `createAsset`, `updateAssetFields`, `deleteAsset`, `allocateAsset`. (Its "enable allocations" toggle originally lived here too as a scoped `toggleProjectAllocations` action — since superseded by the general `updateProjectFields` added for the Manage Projects panel below; the Allocate screen's empty state now calls that instead.)

**Available/Allocated/Retired is deliberately not a stored field** (only `retired` is) — Allocated is derived live from whether a non-done `tasks` row of `kind = 'asset_allocation'` currently carries the asset's id, exactly matching the prototype's `assetDisplayStatus()`. `allocateAsset` creates that allocation task (in an auto-found-or-created "Assets" team within the target project) and hard-links it to the real task via a `clone` link — reusing the existing `addLink()` action so the helpdesk-downgrade safety check stays in one place — rather than duplicating link-insert logic. Since this port's Gantt cascade is a one-shot "Auto-arrange" action rather than a live drag cascade (see the Gantt section above), the allocation task's dates are simply copied from its target at creation time instead of running a live `propagateSchedule`; running Auto-arrange later re-syncs them if the target's dates change.

## Activity log (ported)

Ported from the prototype's `logActivity()`/`activityHtml()` — the task panel's Activity section and the Dashboard's "Your recent activity" feed, both previously dropped for lack of a persisted equivalent (flagged in `schema.sql`'s old "Deliberately deferred" note and in this README's own "Not done yet" list). Scope matches the prototype exactly: only a task's creation and its status moves are recorded, nothing else (no field-edit history, no comment/attachment events).

- `schema.sql` (MODIFIED) / `activity_log.sql` (NEW, run once against an existing database) — the `activity_log` table: `type` restricted to `created`/`status` by a check constraint, `from_status_id`/`to_status_id` only populated for `status` entries (both `on delete set null`, so deleting a workflow status later doesn't destroy history), and — reusing the same nullable-pair pattern `ticket_messages` already established — `actor_user_id`/`actor_contact_id`, so a Portal submission's auto-created task (which runs under the service-role client, with no signed-in user) can still be attributed to the submitting contact. RLS is the same uniform `is_org_member(org_id)` policy every other table here uses; append-only is an app-level convention (nothing ever updates or deletes a row), not something enforced by the database.
- `lib/types.ts` → `ActivityType`, `ActivityLogEntry`.

## Custom subdomains (built — Phase 3, slice 2)

The second slice of Phase 3: each org's public Portal reachable at its own subdomain (`acme.yourapp.com`) instead of only `yourapp.com/portal/acme`, plus the data model and settings UI for a real bring-your-own-domain feature — deliberately without wiring live routing for that second part, for a reason explained below.

- `middleware.ts` (MODIFIED) — `orgSlugForHost()` checks the request's `Host` header against `NEXT_PUBLIC_ROOT_DOMAIN`: a request for `<slug>.<root domain>` gets rewritten (server-side, the browser's address bar is untouched) straight to the existing `/portal/<slug>` route, query string preserved (so a QR code's `?asset=<id>` pre-fill still works). Entirely opt-in — with `NEXT_PUBLIC_ROOT_DOMAIN` unset (the default), this check always returns null and every request behaves exactly as before. Reserved names (`www`, `app`, `api`, `admin`) and nested subdomains never match, so they fall through to normal routing rather than being treated as an org slug. Subdomain requests also skip the `@supabase/ssr` session-refresh this middleware otherwise does on every request — pointless there, since the Portal has no login concept, and skipping it saves a round trip for anonymous visitors.
- `schema.sql` (MODIFIED) / `domains.sql` (NEW, run once against an existing database) — `orgs.custom_domain` (nullable `text`) plus a case-insensitive partial unique index, so two orgs can't claim the same domain. `orgs_admin_update`, the RLS policy from the earlier roles/invites pass, already covers writing to it — no new policy needed.
- `lib/actions.ts` → `updateOrgDomain(orgId, domain)` (owner/admin only, same gate as every other org-settings action): validates the input is a plausible bare hostname (no `https://`, no path), rejects a value that lands inside the platform's own reserved `NEXT_PUBLIC_ROOT_DOMAIN` subdomain space (a custom domain claiming that space would collide with or be shadowed by the subdomain routing above), and gives a friendly "already in use" message on the unique-index violation rather than a raw Postgres error.
- `components/org-settings-panel.tsx` (NEW) — a new "Organization" panel (its own sidebar button, since this is the first settings concern that's about the org itself rather than one of its workspace parts): shows both Portal URLs (the subdomain one, when configured, and the always-works path-based one), and, owner/admin only, the custom-domain field.
- `.env.example` — `NEXT_PUBLIC_ROOT_DOMAIN`, with a note that subdomains of `localhost` resolve in most browsers with no extra setup, so this is testable locally (`http://acme.localhost:3000`) without touching DNS at all.

**Why the custom-domain half is data-model-and-UI only, not live:** routing real production traffic on `orgs.custom_domain` would mean trusting whatever an org owner typed into a text field — nothing here proves they actually control that domain. A malicious or just-mistaken entry could claim a domain that later, coincidentally or not, points its DNS at this same deployment, and traffic meant for that domain would land on this org's Portal. A real "bring your own domain" feature closes that gap with an ownership check (a DNS TXT-record challenge, or delegating to your hosting platform's own Domains API — e.g. Vercel's, which does exactly this before issuing SSL for a custom domain) before ever routing on the value. That verification step needs a real hosting platform connected and isn't buildable or testable from here — this pass lays down everything up to that point (the column, the uniqueness constraint, the settings UI, the validation) so wiring the actual verification in later is additive, not a rework. The subdomain half above has no such gap: `<slug>.NEXT_PUBLIC_ROOT_DOMAIN` is a name the platform itself issues, so there's no ownership question to verify.

## Billing (Stripe) (built — Phase 3, slice 3)

The third and last planned slice of Phase 3: a first pass at Stripe subscription billing per org — subscribe, manage, and keep `orgs`' Stripe columns in sync via webhook. Deliberately single-plan and with **no enforcement anywhere in the app** — see the scoping note below before treating this as more than a first pass.

- `schema.sql` (MODIFIED) / `billing.sql` (NEW, run once against an existing database) — four new columns on `orgs`: `stripe_subscription_id`, `stripe_price_id`, `subscription_status`, `subscription_current_period_end` (alongside `stripe_customer_id`, which was already there from the very first schema pass). All four are written **only** by the webhook below, under the service-role client — no new RLS policy needed, since `orgs_admin_update` doesn't cover them and a webhook bypasses RLS entirely anyway, same as every other webhook handler in this app. `subscription_status` mirrors Stripe's own `Subscription.status` strings verbatim (`active`/`trialing`/`past_due`/`canceled`/...) rather than a reinvented vocabulary; `null` across all four columns means "never started a subscription," not "inactive."
- `lib/types.ts` → `SubscriptionStatus`, and the four new fields on `Org`.
- `lib/billing.ts` (NEW) — two server actions: `createCheckoutSession(orgId)` (lazily creates a Stripe Customer on first use, starts a subscription-mode Checkout Session against the single `STRIPE_PRICE_ID`) and `createBillingPortalSession(orgId)` (Stripe's own hosted "manage your subscription" page — nothing custom-built for cancel/payment-method/invoices, since Stripe's Customer Portal already is that feature). Both are owner-only, gated tighter than the rest of the Organization panel (custom domain there is owner/admin) — day-to-day workspace use doesn't need the ability to change what the org is charged. Both return `{ url }` rather than redirecting server-side: a Server Action's `redirect()` throws a special error that's easy to accidentally swallow in a generic `try/catch` (every panel in this app wraps its actions in one), so the caller navigates the browser itself instead.
- `app/api/webhooks/stripe/route.ts` (NEW) — verifies the Stripe signature (`STRIPE_WEBHOOK_SECRET`), then handles `checkout.session.completed` (correlates back to the org via the Checkout Session's `client_reference_id`, set at creation in `lib/billing.ts`) and `customer.subscription.created`/`updated`/`deleted` (looks the org up by `stripe_customer_id` instead, since those events carry the customer, not the org). Both paths funnel through one shared `syncSubscriptionToOrg()` helper so the four columns can't drift out of sync between the two event families. Every other event type is ignored — this isn't a general Stripe event log, just enough to keep `orgs` in sync.
- `components/org-settings-panel.tsx` (MODIFIED) — a new "Billing" section: current status/plan/period-end when subscribed, a "Subscribe" or "Manage billing" button otherwise, owner-only (an admin sees a message explaining why they can't).
- `.env.example` — `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_ID`. Leave unset to skip billing entirely — the panel just says it isn't configured.
- `package.json` — added the `stripe` SDK.

**Scoping decisions, disclosed:** this is one plan (one `STRIPE_PRICE_ID`), not a tiers system — extending to real tiers later is additive (a plan picker instead of a fixed price id in `createCheckoutSession`), not a rework. More importantly: **nothing in the app checks `subscription_status` to gate access to anything.** What "free" vs. "paid" should unlock is a product decision nobody's made yet, and bolting on an enforcement check prematurely would just be guessing at requirements — this slice only wires up the subscribe/sync/manage mechanics so that decision can be made and implemented on top of real, working billing state, whenever it's ready to be made.

**Untested end-to-end, disclosed plainly:** this environment has no Stripe account connected and no way to click through hosted Checkout or receive a real webhook delivery. The code follows Stripe's Node SDK contract carefully, but run through a real test-mode subscribe/cancel cycle yourself — `stripe listen --forward-to localhost:3000/api/webhooks/stripe` while testing locally — before trusting it in production.

Month view renders as six independent week-rows (each its own CSS Grid, multi-day bars drawn with `grid-column: start / span N`, no per-pixel JS); Week view is the same grid at a larger scale, with a "By person" toggle that swaps it for a grid of one row per visible team member × one column per day, showing an empty day as a "+" that opens an "Allocate to `<Name>`" panel.
- Wired into `components/tasks-workspace.tsx` and `app/dashboard/page.tsx` alongside the existing views; reuses the Gantt/List/Buckets project-team sidebar filter for which tasks are in scope.
- **Disclosed design decisions:** event/bar coloring uses the same `TaskRow.teamColor` accent every other ported view (List/Buckets/Gantt) already uses — the original prototype's "mine vs. others" muted convention was never actually carried into this port's other views, so Calendar matches what's really here instead of a prototype behavior nothing else uses. Clicking an event opens the same task detail panel every other view uses (no separate floating preview card exists in this port). "Allocate to `<Name>`" reuses the existing `updateTaskFields` action — it sets the assignee and moves the task to start on the clicked day, keeping its original duration, but deliberately does **not** re-run the dependency cascade live, matching Auto-arrange's existing one-shot-action design; run Auto-arrange afterward if the allocated task is linked to others. "Eligible backlog tasks" for the allocate panel means tasks still sitting in the `backlog` workflow status whose team (if any) would accept that person under the same `eligibleAssignees()` rule the Assignee dropdown uses. The tree filters strictly by person — an unfiltered calendar shows every scheduled task including unassigned ones, but the moment anyone is unchecked, unassigned tasks drop out of view since there's no one for them to match against.

## Not done yet

Real-time schedule propagation on the Allocate flow (currently a one-shot copy, matching the Gantt's own one-shot Auto-arrange simplification), scoping Auto-arrange to the sidebar's active project/team filter (see above — it's currently org-wide) — plus, from the Gantt view, all the drag-driven interactivity listed above, from the Knowledge base, rich text/images and the stacked article+task panel, and from the Portal, a real live-chat widget and asset-aware pre-fill. The email/WhatsApp channel adapters are now built (see above), but real per-org WhatsApp numbers, message templates for restarting a stale 24h+ conversation, and rendering a submitted Portal form's answers back on the internal task panel (a "form"-kind task_object still shows the generic "not supported" stub there) are all still open. Manual light/dark theme switching (the prototype's sidebar toggle) is deliberately deferred to a broader visual pass rather than ported now — the app already gets dark mode automatically from `prefers-color-scheme`, so only the manual override is missing. The prototype's "Reset sample data" button isn't being ported at all — it was a `localStorage`-only concept with no sensible equivalent against a real database. All three slices of Phase 3 are now built (signup + invites, org subdomains, Stripe billing — see above), leaving two disclosed loose ends rather than unstarted work: real DNS-verified custom domains (the data model and settings UI are there, but nothing routes on an unverified `custom_domain` yet — see "Custom subdomains" above for why) and billing enforcement (subscription state is tracked and kept in sync, but nothing in the app actually checks it — see "Billing" above). This is Phase 0/1/3 of the roadmap: enough real structure to start porting features into, not a feature-complete rebuild.
